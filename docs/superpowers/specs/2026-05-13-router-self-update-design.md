# Дизайн автообновления на роутере

## Цель

Добавить обновление `vpn-manager` прямо с роутера: из публичного GitHub Release или через ручную загрузку архива из браузерного UI.

Первая версия рассчитана только на роутерную сборку `linux/arm64`. В локальной desktop-среде UI может показываться, но установка обновления должна возвращать понятную ошибку, что это поддерживается только на Linux-роутере.

## Источники обновления

### Публичный GitHub Release

Источник по умолчанию берём из текущего git remote:

`DeMoN21207/xiaomi-router-driver-2`

API обновления проверяет latest release через публичный GitHub API без токена и ищет asset с архивом роутерного bundle. Ожидаемое имя asset:

`vpn-manager-linux-arm64.tar.gz`

Источник остаётся настраиваемым в состоянии приложения, чтобы позже можно было поменять публичный репозиторий или шаблон имени asset без переписывания кода.

### Ручная загрузка архива

В UI будет загрузка локального архива с компьютера. Этот путь использует тот же валидатор и установщик, что и скачивание с GitHub. Он нужен для тестовых локальных билдов, частных экспериментов и случаев, когда роутер не может достучаться до GitHub.

## Формат bundle

Архив должен распаковываться в дерево, эквивалентное `build/router`, и содержать:

- `vpn-manager`
- `start.sh`
- `bundle-info.txt`
- `bin/openvpn`
- `bin/sing-box`

В `bundle-info.txt` должны быть значения:

- `goos=linux`
- `goarch=arm64`
- `binary=vpn-manager`

Установщик отклоняет архив, если в нём нет обязательных файлов, указан неправильный target, бинарники пустые, есть path traversal, symlink уводит наружу из директории распаковки или тип архива не поддерживается.

## Backend API

Добавляем endpoints под `/api/system/update`:

- `GET /api/system/update`: вернуть настройки обновления, установленный bundle-info, результат последней проверки и активную операцию, если она есть.
- `PUT /api/system/update/settings`: сохранить настройки публичного источника обновления.
- `POST /api/system/update/check`: проверить latest release на GitHub и запомнить найденный asset.
- `POST /api/system/update/install`: скачать последний найденный или свежепроверенный публичный release asset и установить его.
- `POST /api/system/update/upload`: принять multipart upload архива из браузера и установить его.

Одновременно может выполняться только одна операция обновления. Параллельные установки получают `409 Conflict`.

## Процесс установки

1. Создать рабочую директорию обновлений в `data/.vpn-manager/updates`.
2. Скачать или принять архив в эту директорию.
3. Распаковать архив в изолированную временную директорию с безопасной проверкой путей.
4. Проверить обязательные файлы и `bundle-info.txt`.
5. Создать backup в `backups/update-YYYYMMDD-HHMMSS`.
6. Скопировать текущие runtime-файлы, кроме `data/`, в backup.
7. Оставить текущую `data/` на месте.
8. Заменить runtime-файлы в app directory файлами из проверенного bundle.
9. Выставить executable bits на `vpn-manager`, `start.sh`, `bin/openvpn`, `bin/sing-box`.
10. Записать событие об успехе или ошибке.
11. После HTTP-ответа перезапустить сервис.

Директория `data/` никогда не удаляется установщиком. Если скачивание, распаковка или проверка архива падают, текущий запущенный сервис не трогаем.

## Перезапуск

На Linux после успешной установки API сначала отвечает клиенту, затем планирует коротко отложенный restart. Команда restart повторяет подход текущего deploy:

- Если доступен `/sbin/start-stop-daemon`, остановить текущий pid file и запустить `./vpn-manager` из app directory.
- Иначе запустить `./vpn-manager` в фоне и дать текущему процессу завершиться.

Ответ возвращается до выхода процесса, чтобы UI успел показать состояние перезапуска.

## UI

В Settings появится секция `Обновления`:

- Текущий установленный target из `bundle-info.txt`.
- Публичный репозиторий и шаблон asset.
- Кнопка `Проверить обновление`.
- После проверки: версия release, дата, asset name и размер.
- Кнопка `Установить обновление`, если найден подходящий asset.
- Кнопка/поле `Загрузить архив` для локального `.tar.gz`.
- Состояния операции: проверка, скачивание, установка, перезапуск, ошибка, успех.

После запроса установки UI показывает короткое состояние `сервис перезапускается` и повторяет `/api/status`, пока сервис снова не станет доступен.

## Ошибки

Ошибки возвращаются обычным JSON API error и пишутся в журнал событий. Ожидаемые пользовательские ошибки:

- GitHub release не найден.
- Подходящий asset не найден.
- Скачивание не удалось.
- Архив некорректный.
- Bundle не для `linux/arm64`.
- Не хватает обязательного runtime-бинарника.
- Уже выполняется другая операция обновления.
- Установка обновления не поддерживается на не-Linux хосте.

## Тестирование

Backend tests:

- Выбор подходящего asset из GitHub release.
- Безопасная распаковка отклоняет path traversal.
- Валидатор принимает корректный `linux/arm64` bundle.
- Валидатор отклоняет отсутствующие файлы и неправильную платформу.
- Установщик сохраняет `data/` и создаёт backup.
- Параллельная установка возвращает conflict.

Frontend verification:

- Settings page показывает секцию обновлений.
- Кнопки check/install/upload показывают loading и ошибки.
- Upload отправляет multipart form data.

## Не входит в первую версию

В первой версии нет приватных GitHub токенов, криптографической подписи архивов, автоматического обновления по расписанию и rollback-кнопки в UI. Backup layout делает ручной rollback возможным, а UI rollback можно добавить отдельным следующим шагом.
